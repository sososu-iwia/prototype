# Безопасность и эксплуатация

Актуальный прогон 24 октября 2026: [RELEASE_FINALIZATION.md](RELEASE_FINALIZATION.md). Production проверяет и PUBLIC_ORIGIN, и TRUSTED_ORIGINS как точные HTTPS origins без пути/credentials/wildcard; опечатка MEDIA_STORAGE останавливает запуск. Ошибки oversized JSON возвращают 413 без тела запроса/stacktrace, приватные ответы имеют no-store и при parser error.

Совместимым обновлением lockfile установлен body-parser 2.4.0: исправление [CVE-2026-111181 / GHSA-27r3-jxmh-p828](https://github.com/expressjs/body-parser/security/advisories/GHSA-27r3-jxmh-p828). Регрессионный тест отправляет поздние байты после сжатого HTTP body и проверяет, что API продолжает отвечать. Дерево Express проверено без invalid/duplicate несовместимых подстановок; весь стек не обновлялся. Последний npm audit и его дата — в отчёте, это не гарантия отсутствия будущих advisories.

Дополнительно зафиксированы [Multer 2.5.0](https://github.com/expressjs/multer/security/advisories/GHSA-q7qp-rjg7-q26m) и [fast-uri 3.1.9](https://github.com/fastify/fast-uri/security/advisories/GHSA-w74x-v6f9-j3xg). Nest platform 12.1.3 закреплял вложенный Multer 2.4.0, поэтому root override заменяет все копии на совместимый 2.5.0; принудительный downgrade Nest не применялся. Обычный npm update оставлял уязвимую вложенную копию; targeted install через npm 11.19.1 исправил lockfile. Регрессионный integration проверяет реальные module resolutions API/Nest для Multer и body-parser, а не только lockfile. Новый advisory Multer касается async fileFilter; такой фильтр приложение не использует, но уязвимый пакет всё равно заменён. Override нужно пересмотреть, когда upstream закрепит исправленную версию.

У npm 11.6.2 команда ls помечает этот workspace override как invalid, хотя чистая ci устанавливает обе реальные копии 2.5.0, audit=0 и parser regression проходит. Диагностика того же дерева через npm 11.19.1 ls завершилась 0; глобальный npm пользователя не менялся. Этот [известный класс ошибок CLI](https://github.com/npm/cli/issues/9514) отделён от runtime-проверок; оба лога сохранены.

Недоступность S3/БД при чтении upload возвращает 503 MEDIA_UNAVAILABLE; отсутствующий объект — 404. Оба ответа no-store, поэтому краткий сбой не превращается в закешированный на год «пропавший файл». Upload limit применяется только к загрузке, а не к просмотру медиатеки.

Исправлена подтверждённая гонка login/deactivation: после Argon2 сервер под общей mutation lock повторно проверяет active/version/passwordHash перед созданием Session. Изменившийся или выключенный аккаунт получает 401. Медленная проверка пароля остаётся вне блокировки. Регрессия приостанавливает Argon2, деактивирует EDITOR через настоящий admin API, затем продолжает login и проверяет 401/нулевое количество сессий. До правки тест получал 201; после — regression PASS; финальный расширенный integration-набор 41/41 под DML-ролью.

Production URL API отделён от владельца миграций (`API_DATABASE_URL`). Шаблон DML grants: `infra/runtime-role.sql`; реальную роль/пароль создаёт DBA. Проверены отсутствие SUPERUSER/CREATEDB/CREATEROLE/BYPASSRLS, запрет DDL и работа API под такой ролью в отдельной локальной базе. Это не утверждение, что доступы реального сервера уже настроены. Каталоги backup и dump-файлы дополнительно исключены из Docker build context.

Финальный audit от 24 октября: 0 vulnerabilities; source scan PASS. Физические parser resolutions повторно проверены в Linux production image (Multer2.5.0/body-parser2.4.0), PG server/client17.11. Local TLS drill с COOKIE_SECURE=true/ALLOW_LOCAL_HTTP=false проверил 8 групп, включая chain/hostname, Origin, CSRF, cookie flags, S3 upload/delete и отзыв сессии; системное доверие сертификатам не изменялось. Это одноразовая CA/протокольная fixture, не публичный ACME/IAM. В успешных runtime-логах есть nonfatal предупреждение pg8.23.1 о queued queries; будущий pg9 не сертифицирован, необоснованный upgrade не выполнялся.

## Реализовано

- Пароли Argon2id: 64 MiB, 3 прохода, parallelism 1 при bootstrap. У неизвестного email выполняется проверка dummy hash с той же стоимостью. Публичной регистрации и мастер-паролей нет. Новые операторы создаются через защищённую консольную команду, существующий пароль она не заменяет.
- Сессия — криптографически случайный token; в БД только SHA-256 token/CSRF. Cookie HttpOnly, SameSite=Strict, Secure на HTTPS, TTL 8 часов. Logout удаляет серверную сессию. Деактивированный User или истёкшая сессия не допускаются. Access/refresh tokens не помещаются в localStorage.
- Любое изменение требует разрешённого Origin и CSRF header, связанного с сессией. Login проверяет Origin отдельно. CSRF-token хранится только в памяти клиента и восстанавливается через защищённый GET. CORS — конкретный список TRUSTED_ORIGINS, без `*`.
- SUPER_ADMIN управляет всеми ролями. ADMIN ведёт клуб и может управлять только EDITOR; EDITOR ведёт свои новости/галерею/медиа. Футбольные данные, чужие новости, настройки и журнал защищены на сервере. Деактивация/смена роли/пароля отзывает сессии. Исторические данные архивируются; физическое удаление запрещено.
- Все write DTO — Zod `.strict()`, ограниченные поля, длины, enum, числа, даты и локали. Prisma параметризует SQL; пользовательский SQL отсутствует. Финальный счёт и разные участники матчей валидируются. Черновики/будущие публикации исключены и из списка, и из детальной статьи.
- Статьи и preview используют **plain text**, отображаемый React с escaping. HTML/Markdown с raw HTML не исполняются. Arbitrary page builder и редактор кода отсутствуют.
- Upload: только JPEG/PNG/WebP, MIME/суффикс/magic bytes, максимум 10 MiB и один файл, лимит 40 млн пикселей. Sharp создаёт WebP/AVIF до 1920 px и WebP thumbnail и удаляет метаданные; SVG/HTML/исполняемые файлы не принимаются. UUID filename, durable storage вне кода, `nosniff`/закрытая CSP на выдаче.
- Login rate limit: 10 неуспешных попыток за 15 минут на IP; API 1000/min; upload 20/min. По умолчанию X-Forwarded-For игнорируется. Production overlay явно доверяет приватной сети Caddy (`TRUST_PROXY_CIDRS=uniquelocal`); внешний порт API отсутствует, Caddy очищает недоверенные forwarding headers. Отдельные клиенты получают независимые лимиты. Тесты проверяют и запрет обхода через поддельный header при прямом доступе, и раздельные лимиты за доверенным proxy. Для нескольких API нужен общий limiter.
- CSP nonce на каждый frontend response; без unsafe-inline для scripts, без объектов/iframes, form-action self. Inline styles разрешены из-за исходного CSS/React. `nosniff`, Referrer-Policy, Permissions-Policy, frame deny, HSTS на HTTPS. API использует Helmet.
- Production config требует Secure cookies и HTTPS origins. Локальное HTTP-исключение допускает **только localhost/127.0.0.1 origins**, Compose web привязан к 127.0.0.1. В production overlay это исключение выключено. Не задавайте ALLOW_LOCAL_HTTP=true для публичного сервера.
- Provider работает только на сервере с фиксированным разрешённым upstream URL. Timeout 5s, максимум 3 попытки, backoff, 429 cooldown, Zod response validation, TTL и последнее успешное значение с датой/stale. В лог не записывается API key.
- Структурированные request/error logs содержат requestId, метод, path без query, status и duration. Пароли/cookies/тела запросов не логируются. AuditLog фиксирует изменения в одной транзакции с ними. Ошибки API не возвращают stacktrace.

## Обязательная конфигурация оператора

Разные длинные пароли БД и администраторов; `.env` не коммитить. Файлы backup содержат персональные данные и hashes, хранить зашифрованно вне VPS. Доступ к SSH/volume/базе ограничить. Не публиковать порты Postgres и API. Нужен firewall, регулярные обновления Node/Docker/ОС и backup/restore drill.

Имеющиеся изображения/видео сохранены по заданию; право публичного использования должен подтвердить владелец. API-Football подключается только при наличии допустимой подписки/лицензии. Реальные текущие персоналии/матчи не подтверждены автоматически.

## Пределы проверки

`npm audit`, pattern secrets scan, typecheck, integration и axe не заменяют независимый penetration test. Rate limiter в памяти предназначен для одного API instance. Нет MFA/SMTP password reset/антивирусного карантина/пользовательских видео-upload; эти механизмы не имитируются. Reset-flow намеренно отсутствует. Восстановление оператора выполняется через контролируемую серверную процедуру и аудит, а не скрытый bypass.

Источники подходов: [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html), [Next.js security release](https://nextjs.org/blog/nextjs-security-update-october-14-2026). Версии реально установленных пакетов закреплены lockfile; критические advisories исправлялись обновлением поддерживаемых majors, без `--force`/отключения peer checks.


PUT/DELETE требуют If-Match; устаревшая версия не перезаписывается. Content mutations и проверка использования медиа сериализованы PostgreSQL advisory lock; интервалы состава защищены exclusion constraint. Идемпотентные POST хранят результат в БД. Журнал сохраняет безопасную разницу и SUCCESS/FAILURE; длинный текст сокращается. CSRF стабилен для сессии, позволяя работать в нескольких вкладках. Production требует S3; credentials остаются на backend, браузер получает только same-origin пути. Для нескольких API replicas нужен общий rate-limit store (текущий limiter остаётся процессным).
